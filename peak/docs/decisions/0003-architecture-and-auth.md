# 0003 — App architecture, module split and Roblox auth flow

- **Date:** 2026-10-05
- **Status:** accepted
- **Skills consulted:** ios-dev, guide-swift-concurrency (actors.md, bug-patterns.md),
  roblox-cloud, widgetkit

## Context

The app, the widget extension and (later) a Swift backend share models and logic: goal
maths, alert rules, number formatting, deep links and widget snapshots. Roblox OAuth
refresh tokens rotate, so concurrent refreshes can invalidate each other. Per
`roblox-cloud`, code exchange and refresh should run on a trusted backend, and rotated
tokens must be replaced atomically with a single owner.

## Decision

### Modules

- `Packages/PeakKit`: a platform-neutral Swift package (Foundation only, so it builds
  and tests on Linux CI). It contains models, `GoalEngine`, `AlertEngine`, campaign maths,
  formatting, `Route` deep links, `WidgetSnapshot` + `SnapshotStore`, `APIClient`,
  `AuthSessionCoordinator` and sample data.
- `Peak` (app target): SwiftUI views and `@MainActor @Observable` models. No business
  logic in `body` (ios-dev checklist).
- `PeakWidgets` (widget extension): reads `WidgetSnapshot` only. It never calls the
  network itself. Widgets are cached snapshots.
- The project file is generated by XcodeGen from `project.yml`. No hand-edited `.pbxproj`.

### Auth

1. App → backend `POST /v1/auth/roblox/start`. The backend creates `state` and the PKCE
   verifier/challenge and returns the Roblox authorize URL.
2. The app opens it in `ASWebAuthenticationSession`. Roblox redirects to the **backend**
   callback, which verifies `state`, exchanges the code (confidential client + PKCE) and
   stores the Roblox tokens server-side.
3. The backend redirects to `peakstats://auth/complete?code=<one-time session code>`. The app
   exchanges that for an **Peak session** (short access token + rotating refresh token).
4. The app stores only the Peak session, in the Keychain. Roblox tokens never reach
   the device.
5. On the client, `AuthSessionCoordinator` (an actor) owns refresh. There is one in-flight
   refresh `Task`, and every caller awaits it. A 401 refreshes only if the failed token is
   still the current one, and the new token pair is saved before it's handed out. On the
   backend, the same rule applies per Roblox account (one lock per account).

The in-flight refresh `Task` is the one deliberate unstructured task in the module. Its
owner is the actor, and it's cleared on completion. It isn't tied to any single caller,
so one cancelled caller can't abort a refresh other callers depend on.

### Monitoring

Alert evaluation for notifications runs on the backend, which sends APNs. `AlertEngine`
lives in the shared package so the backend and the in-app "preview this rule" feature
use identical logic.

## Alternatives considered

- **Public-client PKCE entirely on device** — puts rotating Roblox refresh tokens on every
  phone and makes the server-side monitoring that alerts need impossible. Rejected.
- **One big app target** — the widget would link UI code, and the logic couldn't be tested
  without a simulator. Rejected.

## Consequences

- A backend is required before real data flows. Until then the app runs on
  `DemoDashboardService` (sample data), selected automatically when no API base URL is
  configured.
- The backend contract is documented in `docs/api/backend-contract.md`.
